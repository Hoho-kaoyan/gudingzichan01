# 安全检查任务：管理员与组长权限方案

## 需求摘要

1. **管理员角色可以有自己的安全检查任务**：管理员作为资产使用人时，应能像普通用户一样接收、查看并完成自己的安全检查任务。
2. **组长可以在组内发布安全检查任务**：组长可发布任务，但仅能选择本组资产，任务执行人仍为资产使用人（本组成员）。

---

## 一、现状简述

| 能力 | 当前实现 |
|------|----------|
| 创建任务 | 仅管理员可创建（`get_current_admin_user`） |
| 任务分配 | 按资产使用人 `asset.user_id` 作为 `assigned_user_id`，无按人指定 |
| 任务列表 | 管理员看全部；非管理员只看「分配给自己的」 |
| 我的安全任务 | 任意登录用户均可访问，按 `assigned_user_id == current_user.id` 拉取 |
| 提交检查结果 | 仅分配给自己的任务可提交，不区分角色 |

管理员若为某资产的使用人，理论上已会出现在「我的安全任务」并可完成；需确认前端菜单/入口对管理员可见且无限制。

---

## 二、方案一：管理员有自己的任务（最小改动）

**结论**：现有逻辑已支持「管理员作为使用人时有自己的任务」，只需保证前端一致。

- **后端**：无需改。`get_my_tasks`、`get_task_assets_for_user`、`submit` 均按 `assigned_user_id == current_user.id`，不排除 admin。
- **前端**：
  - 确保「我的安全任务」菜单对**所有登录用户**（含管理员、组长）展示并可进入。
  - 若当前仅对「非管理员」展示，改为管理员也可见、可操作（查看待检查/已完成、进入任务、提交结果）。

**可选扩展**（若产品后续要求）：支持管理员在「创建任务」时，将某些资产的任务挂到自己名下（即 `assigned_user_id = 管理员`，即便管理员不是该资产使用人）。需要再扩展创建任务接口（如按资产指定执行人），本方案不包含。

---

## 三、方案二：组长可在组内发布任务（推荐实现）

### 3.1 权限与范围

- **发布权限**：组长与管理员均可「创建」安全检查任务。
- **组长可选资产范围**：仅限**本组资产**（`asset.user_group == current_user.group`），且资产需有使用人。
- **任务分配规则不变**：每条任务资产仍按 `assigned_user_id = asset.user_id`（即资产使用人），组长不改变执行人逻辑。

### 3.2 后端改动要点

| 模块 | 改动 |
|------|------|
| **auth** | 新增 `get_current_admin_or_leader`：仅 admin 或 leader 可通过，用于「创建/更新/取消」任务。 |
| **创建任务** | 依赖改为 `get_current_admin_or_leader`。若当前用户为 **leader**：校验 `task_data.asset_ids` 中所有资产均满足 `asset.user_group == current_user.group` 且未删除、有使用人；不满足则 400。 |
| **任务列表** `get_tasks` | **leader** 可见范围：① 自己创建的任务（`SafetyCheckTask.created_by_id == current_user.id`），② 或任务中存在「分配给自己的」资产（`TaskAsset.assigned_user_id == current_user.id`）。即组长看到「我发布的」+「分配给我的」。 |
| **任务详情** `get_task_detail` | **leader**：若 `task.created_by_id == current_user.id` 可查看；否则仅当存在 `TaskAsset.assigned_user_id == current_user.id` 时可查看（与现有一致）。 |
| **任务资产列表** `get_task_assets` | **leader**：若为任务创建人则返回该任务下全部任务资产（与 admin 一致）；否则仅返回 `assigned_user_id == current_user.id` 的资产。 |
| **更新任务** `update_task` | 依赖改为 `get_current_admin_or_leader`。**leader** 仅可更新自己创建的任务（`task.created_by_id == current_user.id`），否则 403。 |
| **取消任务** `cancel_task` | 同更新：依赖 `get_current_admin_or_leader`，**leader** 仅可取消自己创建的任务。 |

### 3.3 前端改动要点

| 页面/逻辑 | 改动 |
|-----------|------|
| **安全任务管理** | 入口与数据加载：不仅 `isAdmin` 可进，**组长（isLeader）也可进入**。加载任务列表、检查类型、大类等逻辑对组长开放；发布任务按钮对 admin 与 leader 均显示。 |
| **发布任务 - 选资产** | 管理员：可选全部资产（保持现有）。组长：仅请求/展示**本组资产**（例如接口增加 `user_group` 或由后端在「可选资产」接口中按组过滤；若沿用现有资产列表接口，则前端传 `user_group=当前用户组` 或仅展示本组资产）。 |
| **路由/菜单** | 「安全任务管理」菜单对 **管理员 + 组长** 可见；「我的安全任务」对所有人可见（含管理员、组长）。 |

### 3.4 接口约定建议

- **获取「可选的」资产列表（用于发布任务）**  
  - 现有：管理员调 `GET /assets/` 等。  
  - 组长：同一接口，后端根据 `current_user.role == "leader"` 自动过滤 `asset.user_group == current_user.group`（若当前资产列表已支持按组过滤，则复用；否则在发布任务用的列表接口中加此过滤）。

---

## 四、数据与角色一致性

- **组长**：`User.role == "leader"` 且 `User.group` 有值；发布任务时仅能选 `Asset.user_group == User.group` 的资产。
- **任务创建人**：`SafetyCheckTask.created_by_id` 记录发布者（管理员或组长），用于列表/详情权限与「谁可更新、取消」。
- 不新增表字段；仅用现有 `created_by_id`、`user_group`、角色做权限与范围控制。

---

## 五、实施顺序建议

1. **方案一**：检查并调整前端「我的安全任务」对管理员（及组长）的展示与可用性；无后端改动。
2. **方案二**：  
   - 后端：auth 增加 `get_current_admin_or_leader` → 创建/更新/取消任务改用该依赖 → 创建任务时组长资产范围校验 → 列表/详情/资产接口的 leader 可见范围与可操作范围。  
   - 前端：安全任务管理页对组长开放，发布任务时组长仅选本组资产；菜单与路由按角色展示。

---

## 六、测试要点

- 管理员作为某资产使用人时，在「我的安全任务」中能看到并完成该任务。
- 组长发布任务：仅能选择本组资产；选他组资产时后端返回 400。
- 组长在「安全任务管理」中只能看到自己创建的任务 + 分配给自己的任务；任务详情/资产列表中，自己创建的任务看全部资产，仅被分配的任务只看自己的资产。
- 组长只能更新/取消自己创建的任务；管理员可更新/取消全部任务。
- 管理员仍可照常发布任务、查看全部任务与资产。
