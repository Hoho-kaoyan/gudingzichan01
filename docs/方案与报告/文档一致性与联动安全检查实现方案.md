# 第二部分：联动安全检查需求与已确认项

## 2.1 需求要点

1. **触发时机**：除管理员在「任务发布」里手动发布外，需要联动安全检查的场景在**发起时**由系统分配一条安全检查任务给对应用户。
2. **后续流程**：该场景涉及的后续步骤（转入人确认、管理员审批、调拨生效、退库/交接提交等）必须在该任务**完成后**才允许进行。
3. **管理员可见性**：管理员在「安全检查任务」列表中能看到**全部**任务（含系统自动创建的）；当前接口已查全表，无需改。
4. **任务类型可配置**：系统自动分配的任务类型由管理员配置——包括**默认检查任务类型**，以及**针对某些固定资产类型的检查任务类型**（如终端→类型a、显示器→类型b）；分配时按当前资产类型匹配，未配置则用默认类型。

## 2.2 您已确认的项


| 序号       | 确认内容                                                                                               |
| -------- | -------------------------------------------------------------------------------------------------- |
| **待确认1** | 批量导入时，仅对「成功入库且带使用人」的资产创建任务，失败行不创建。                                                                 |
| **待确认2** | 交接：**必须已有任务已完成**才允许进行**转入人确认/管理员审批**；**创建交接申请时**由系统分配一条安全检查任务给转出人（即：创建申请时自动创建任务，后续确认/审批前校验该任务已完成）。 |
| **待确认3** | 调拨时若资产**当前无使用人**（在库），管理员将使用人改为 B：由 **B** 做安全检查，系统分配任务给 B，B 完成后调拨才生效（不直接改使用人）。                      |
| **待确认4** | 本期增加**组长**角色；组长可对组内资产进行组内调拨（与管理员调拨联动逻辑一致，权限范围不同）。                                                  |
| **待确认5** | **离职联动纳入本期**：用户状态、标记离职、按配置为该员工名下资产自动发布检查任务、退库/交接前校验。                                               |


## 2.3 自动分配任务类型配置（新增需求）

- **管理员可配置**  
  - **默认检查任务类型**：当资产类型未在映射中时使用。  
  - **按资产类型映射**：针对某些「固定资产类型」配置使用的检查任务类型（如：终端→任务类型a，显示器→任务类型b）。
- **系统自动分配时**  
  - 根据**当前资产类型**查映射；若该资产类型已配置则用对应检查类型；否则用默认检查任务类型。  
  - 若当前资产类型未配置且未配置默认类型，则不创建任务并打日志。
- **资产类型**  
  - 与资产实体的**实物名称**字段对应，即 `assets.name`（实物名称）。配置中的「资产类型」如终端、显示器等，即为实物名称的取值；分配时用当前资产的 `name` 去查映射，匹配则用对应检查类型，否则用默认。

# 第三部分：联动场景与逻辑梳理

## 3.1 场景一：资产入库（单个 + 批量）

- **触发**：单个 `POST /api/assets/` 成功且 `user_id` 非空；批量导入每成功写入一条且该行有使用人。
- **动作**：按**当前资产实物名称**解析出的检查类型（见 2.3），为该资产、该使用人创建 1 条任务（1 task + 1 task_asset）。
- **后续**：入库无阻塞；该资产日后被交接时，在交接流程中校验「当前所有人」是否仍有未完成任务，有则不允许确认/审批。

## 3.2 场景二 情况一：员工发起交接

- **触发**：`POST /api/transfers/` 创建交接申请，资产当前有使用人（转出人 A）。
- **动作**：  
  - 若该资产对 A 已有**未完成**（pending/overdue）的 task_asset：**不允许创建申请**，返回 400，提示「请先由当前所有人完成数据安全检查」。  
  - 若没有未完成任务：为该资产、assigned_user_id = A 创建一条新任务（检查类型按 2.3 规则），再创建交接申请。
- **后续**：转入人确认、管理员审批前，校验该资产对**转出人 A** 是否仍有未完成任务；有则拒绝并同一提示。只有 A 完成检查后，才允许确认与审批通过。

## 3.3 场景二 情况二：管理员/组长调拨

- **有原所有人 A，改为 B**  
  - 不直接改 `assets.user_id`。  
  - 为资产、assigned_user_id = **A** 创建一条任务（检查类型按 2.3）。  
  - 写入待生效调拨：asset_id、new_user_id=B、task_id。  
  - A 在「我的检查任务」完成该任务后，在提交检查结果逻辑中检测任务完成，将对应资产的 user_id/user_group 更新为 B，并删除该条待生效调拨。
- **当前无使用人（在库），改为 B**  
  - 不直接改 `assets.user_id`。  
  - 为资产、assigned_user_id = **B** 创建一条任务（检查类型按 2.3）。  
  - 写入待生效调拨：asset_id、new_user_id=B、task_id。  
  - B 完成该任务后，同上，更新资产使用人并删除待生效调拨。
- **组长**：本期新增组长角色；组长仅能对**本组**资产修改使用人（组内调拨），调拨逻辑与管理员一致（待生效调拨 + 任务给 A 或 B）。

## 3.4 场景三：员工离职

- 用户表增加**状态**（如在岗/离职等）；管理员可标记用户为「离职」。
- 标记离职时提示：「是否完成数据安全检查进行资产交接？」→ 选「是」后，按配置（默认或按资产类型）为该员工**名下资产**批量创建检查任务，分配给该员工。
- 该员工在「我的检查任务」完成所有任务后，才允许其提交**资产退回申请**或**交接申请**（退库/交接前校验：其名下资产是否均已完成检查；若有未完成则拒绝提交）。

# 第四部分：可参考的实现方案（不修改代码，仅方案）

## 4.1 数据库与 Model 层

### 4.1.1 新增表


| 表名                                | 用途                | 建议字段                                                                                                       |
| --------------------------------- | ----------------- | ---------------------------------------------------------------------------------------------------------- |
| **safety_check_auto_config**      | 系统自动分配任务类型配置      | id, default_check_type_id（可空）, created_at, updated_at。若仅一个全局配置，可单行；若需按环境/多套配置可加 config_key。                |
| **safety_check_asset_type_mapping** | 实物名称（资产类型）→ 检查类型映射 | id, asset_type（VARCHAR，实物名称取值，如「终端」「显示器」）, check_type_id（FK safety_check_types）, created_at。唯一约束 (asset_type)。 |
| **pending_reallocations**         | 待生效调拨（等任务完成后改使用人） | id, asset_id（FK）, new_user_id（FK）, task_id（FK safety_check_tasks）, created_at。                             |


### 4.1.2 已有表字段调整


| 表                      | 调整                                                                                                        |
| ---------------------- | --------------------------------------------------------------------------------------------------------- |
| **users**              | 新增 `status` 字段，如：VARCHAR(20)，取值如在岗/离职/长期出差/借调/产假等；默认「在岗」。可选新增 `role` 扩展：当前为 admin/user，增加枚举值如 leader（组长）。 |
| **safety_check_tasks** | 可选新增 `source` 字段，标识任务来源，便于列表筛选与统计，非必须。取值含义与使用场景见下。                |


**`source` 字段说明**

- **作用**：区分任务是由管理员手动发布，还是由系统在某一业务场景下自动创建，便于：
  - **列表筛选**：管理员可按「手动发布 / 入库联动 / 交接联动 / 调拨联动 / 离职联动」等维度筛选任务；
  - **统计与报表**：如按来源统计任务数量、完成率；
  - **业务策略**（可选）：如仅允许对「手动发布」的任务做编辑/取消，系统创建的任务仅允许执行与完成。

- **取值含义**：

| 取值 | 含义 | 对应场景 |
|------|------|----------|
| **manual** | 管理员手动发布 | 管理员在「安全检查任务」中通过「发布新任务」选择资产与检查类型后创建的任务 |
| **inbound** | 资产入库联动 | 场景一：单个新增资产或批量导入时，分配给使用人的任务 |
| **transfer** | 交接联动 | 场景二情况一：创建交接申请时，系统分配给转出人的任务 |
| **reallocation** | 调拨联动 | 场景二情况二：管理员/组长改「所有人」时，系统分配给原所有人或新所有人（在库→B）的任务 |
| **resignation** | 离职联动 | 场景三：管理员标记离职并确认后，系统为该员工名下资产批量创建的任务 |

- **使用场景举例**：
  - 管理员在任务列表中筛选「仅看系统自动分配的任务」或「仅看手动发布的任务」；
  - 统计某月「交接联动」产生的任务数及完成率；
  - 若产品约定「系统创建的任务不允许管理员修改截止时间」，可根据 `source != 'manual'` 在前端或接口中禁用编辑。


### 4.1.3 Model 层（参考）

- **User**：增加 `status`；若支持组长，则 `role` 增加 `leader` 枚举值。
- **SafetyCheckType**：无结构变更；配置表仅引用其 id。
- **SafetyCheckTask / TaskAsset**：无结构变更；可选 `source`。
- **PendingReallocation**：新建 Model，字段与上表一致，与 Asset、User、SafetyCheckTask 建关系。
- **SafetyCheckAutoConfig**：新建 Model；若单行配置则仅 default_check_type_id。
- **SafetyCheckAssetTypeMapping**：新建 Model，asset_type（字符串，实物名称取值）、check_type_id，与 SafetyCheckType 建关系。

## 4.2 配置与 Service 层（逻辑参考）

### 4.2.1 自动分配使用的检查类型解析

- **输入**：`db: Session`, `asset_name: str`（资产的实物名称，即 `asset.name`）。入参仅传实物名称，避免加载整条 asset，便于性能与复用。
- **逻辑**：  
1）查 `safety_check_asset_type_mapping` 中 asset_type = asset_name 的 check_type_id；若有则返回。  
2）否则查 `safety_check_auto_config` 的 default_check_type_id；若有则返回。  
3）否则返回空（不创建任务，打日志）。
- **校验**：返回的 check_type_id 对应检查类型需存在且 is_active = true，否则同上按「无配置」处理。
- **返回**：`int | None`（检查类型 id）。

### 4.2.2 创建「单资产、单用户」系统任务（共用）

- **输入**：db, asset_id, assigned_user_id, source（如 inbound/transfer/reallocation/resignation）, 可选 title 前缀。
- **逻辑**：  
1）取 asset，若不存在或已删除则返回。  
2）用 4.2.1 解析出 check_type_id（入参为 asset.name）；若无则返回不创建。  
3）生成任务编号、写入 safety_check_tasks（created_by 可用系统用户或当前操作人 id）、写入一条 task_assets（asset_id, assigned_user_id, status=pending）。  
4）返回 task 或 task_id，供调用方（入库/交接/调拨/离职）使用。

### 4.2.3 场景一：入库（单个 + 批量）

- **单个**：在 `POST /api/assets/` 成功写入资产后，若 asset.user_id 非空，调用 4.2.2 创建任务。
- **批量**：在批量导入循环中，每成功 add + flush 一条资产且 user_id 非空，调用 4.2.2 创建任务；失败行不创建。

### 4.2.4 场景二 情况一：交接

- **创建交接申请**：  
  - 查该 asset + 当前使用人 A 是否存在 status in (pending, overdue) 的 task_asset；若存在则 400「请先由当前所有人完成数据安全检查」。  
  - 否则调用 4.2.2 创建任务（assigned_user_id = A），再创建交接申请。
- **转入人确认**：若确认接收，先校验该 asset 对 request.from_user_id 是否仍有未完成 task_asset；有则 400，同一提示。
- **管理员审批**：若审批通过，同样校验该 asset 对 request.from_user_id 是否仍有未完成 task_asset；有则 400。

### 4.2.5 场景二 情况二：调拨（管理员/组长）

- **权限**：管理员可改任意资产使用人；组长仅可改**本组**资产的使用人（如 asset.user_group == current_user.group 或按组内用户列表约束）。
- **有原所有人 A → B**：不更新 asset.user_id；调用 4.2.2 创建任务（assigned_user_id = A）；插入 pending_reallocations(asset_id, new_user_id=B, task_id)。
- **无使用人 → B**：不更新 asset.user_id；调用 4.2.2 创建任务（assigned_user_id = B）；插入 pending_reallocations(asset_id, new_user_id=B, task_id)。
- **提交检查结果**：在现有「任务完成」逻辑中，若该 task 存在 pending_reallocations，则遍历将对应 asset 的 user_id、user_group 更新为 new_user_id 及其组别，并删除这些 pending 记录。

### 4.2.6 场景三：离职

- **用户状态**：标记离职即更新 users.status = 离职；可选记录状态变更时间或日志。
- **标记离职并确认**：前端二次确认「是否完成数据安全检查进行资产交接？」；确认后，查询该用户名下所有资产（未删除、user_id = 该用户），对每条资产调用 4.2.2 创建任务（assigned_user_id = 该用户），检查类型仍按 4.2.1 按资产实物名称解析。
- **退库/交接前校验**：用户提交退回申请或交接申请时，校验该用户名下是否仍有「未完成」的 task_asset（status in (pending, overdue)）；若有则 400，提示先完成数据安全检查。

## 4.3 配置接口与前端（参考）

- **配置接口**：  
  - GET/PUT 全局配置：默认检查类型（如 GET/PUT `/api/safety-check-auto-config` 或放在系统设置下）。  
  - 实物名称（资产类型）→ 检查类型：列表与增删改（如 `/api/safety-check-asset-type-mappings`），便于管理员配置「终端→类型a、显示器→类型b」。

**GET 映射 与 PUT 映射 的区别**

| 接口 | 作用 | 说明 |
|------|------|------|
| **GET 映射** | 获取「实物名称→检查类型」的**列表** | 只读：返回当前所有配置的映射（如 [{ asset_type: "终端", check_type_id: 1, ... }, ...]），供前端展示、下拉选择等。 |
| **PUT 映射** | **修改**某一条映射 | 更新指定 id 的映射（例如把「终端」对应的检查类型从 A 改为 B）。若不提供 PUT，只能先 DELETE 该条再 POST 新增；提供 PUT 则一次请求即可改 check_type_id，语义更清晰、操作更简单。 |
- **前端**：  
  - 管理员在「安全检查」或「系统设置」中可配置默认检查任务类型、按实物名称（资产类型）的检查任务类型映射表。  
  - 用户管理：用户列表与表单中增加「状态」；管理员可标记离职，并弹出确认「是否完成数据安全检查…」。  
  - 组长：角色/权限中增加组长；资产管理编辑使用人时，组长仅能选本组用户或仅能改本组资产（与现有组别、权限模型一致即可）。

## 4.4 实现顺序建议

1. 数据库：新增表、User 增加 status（及可选 role 扩展）、可选 task.source。
2. 配置：SafetyCheckAutoConfig + SafetyCheckAssetTypeMapping 的 Model、解析逻辑（4.2.1）、配置接口与前端。
3. 共用：4.2.2 创建系统任务的 Service/函数。
4. 场景一：入库（单个 + 批量）调用 4.2.2；交接流程增加「未完成检查不可确认/审批」校验。
5. 场景二 情况一：创建交接时按 4.2.4 创建任务与校验；确认/审批前校验。
6. 场景二 情况二：待生效调拨表与逻辑；管理员/组长改使用人时写 pending + 创建任务；提交检查结果后处理 pending。
7. 组长角色与组内调拨权限。

## 6.2 阶段与先后顺序

### 第 1 阶段（优先，人员 A 为主）

**目标**：后端基础就绪，配置可读可写，其余三人可依赖或联调。

| 顺序 | 负责人 | 工作内容 |
|------|--------|----------|
| 1 | 人员 A | 新增表：`safety_check_auto_config`、`safety_check_asset_type_mapping`（实物名称→检查类型）、`pending_reallocations` 已有；`users` 表增加 `status`、`role` 增加组长枚举；`safety_check_tasks` 可选 `source`；对应 Model 与迁移/建表 |
| 2 | 人员 A | 实现「按实物名称解析检查类型」逻辑（4.2.1）：入参 (db, asset_name)；查映射表与默认类型，返回 check_type_id |
| 3 | 人员 A | 配置接口：默认检查类型与实物名称→检查类型映射的 CRUD（GET/PUT 全局配置、映射列表 GET、POST、DELETE，可选 PUT 单条映射） |

**产出**：表结构、Model、配置解析函数、配置 API 可用。人员 B 可开始调用配置解析与配置数据；人员 C 可对接配置接口做配置页。

### 第 2 阶段（人员 B、C 并行，人员 D 可跟进）

**目标**：入库与交接联动上线，配置页与用户/组长前端就绪，任务列表支持按来源筛选。

| 顺序 | 负责人 | 工作内容 |

| 5 | 人员 B | 场景一：单个入库、批量导入成功后，若使用人非空则调用 4.2.2 创建任务（source=inbound） |

| 7 | 人员 C | 管理员「联动任务类型配置」页：默认检查类型选择、实物名称（资产类型）→检查类型映射的列表与增删改（对接人员 A 的配置接口） |
