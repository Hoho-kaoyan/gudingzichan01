# 文档修订意见

本文档基于对现有代码与 `docs/` 下全部文档的对照，归纳当前文档存在的问题，并给出修订建议。**采纳「已完成事项」与「待办事项」分开记录的意见**，便于后续维护与投产对齐。

### 1.2 文档与代码已对齐、仅需保留表述的

- **实物名称→检查类型映射**：实现与《文档一致性与联动安全检查实现方案》4.2.1 一致，均为按 `asset.name`（实物名称）。但《人员A工作完成情况与人员C工作解析》中仍有「文档按 category_id、实现按 asset_name」的**历史差异描述**，易造成误解，应按《对话整理与待办方案》D1 删除或改写为「文档与实现均已按实物名称」。
- **状态用语**：「库存备用」已统一改为「在库」，代码与 approvals/returns/assets 等已一致。
- **核心功能与联动**：投产范围、联动配置、发布任务、批量导入与入库联动、调拨联动（PendingReallocation）、组长权限等，代码均已覆盖，文档描述基本一致。

### 1.3 文档之间重叠与主从不清

- **测试类**：存在多份测试文档，内容重叠且主从关系不清晰：
  - `核心功能测试优先清单.md`：定义了优先执行顺序与核心用例，含执行记录表与 Bug 记录，但与管理员的默认密码等仍为旧值（如 `admin123`，而 `init_db.py` 已改为 `1234567`）。
  - `功能测试文档.md`：按角色与场景的详细步骤，体量大（1500+ 行），与测试用例文档第一/二部分大量重复。
  - `测试用例文档-第一部分.md` / `测试用例文档-第二部分.md`：表格版用例，与功能测试文档在登录、用户、资产、交接、退回、审批、安全检查等模块重叠。
  - `测试文档260304.md`：基于「当前已完善功能」的测试文档，含方案乙、组长、联动配置等，与核心功能测试优先清单、功能测试文档有交叉引用但未明确「以谁为执行主清单」。
- **方案与报告类**：《对话整理与待办方案》与《人员A工作完成情况与人员C工作解析》中既有「已完成」又有「待办」，混在同一文档中，且待办中不少已在代码中完成，阅读时难以快速区分**当前真正待办**与**历史已闭环事项**。

## 二、文档存在的主要问题归纳

1. **已完成与待办未分离**
  规划、待办、完成情况混在多份文档（对话整理与待办方案、人员A/C工作解析等）中，无法一眼区分「已上线/已实现」与「尚未完成」，不利于投产前核对和排期。
2. **测试文档多而杂**
  测试用例、功能测试文档、测试文档260304、核心功能测试优先清单四类文档存在大量重复；执行顺序与主清单虽有提及，但分散在多处，未形成「一份主清单 + 其余引用」的清晰结构。
3. **过时信息未更新**
  - 默认管理员密码：文档多处仍为 `admin123`，实际 `init_db.py` 已改为 `1234567`（与初始用户配置一致）。  
  - 人员A解析中「按大类 vs 按实物名称」的差异表述仍存在，易误导为尚未统一。  
  - 部分「待办」在代码中已实现，文档未同步为「已完成」。
4. **缺少单一入口的「已完成清单」与「当前待办」**
  没有一份专门文档（或专门章节）只列：  
  - **已完成事项**（含对应文档/代码位置，便于验收与回归）；  
  - **当前待办事项**（仅列尚未实现或尚未闭环的内容），导致信息分散、重复维护。

## 三、修订建议（含「已完成」与「待办」分开记录）

### 3.1 总体思路

- **采纳「已完成」与「需要做的事情」分开记录**：  
  - 建议在 `docs/` 下通过**单独文档或固定章节**维护两类清单：**已完成事项清单**、**当前待办事项清单**。  
  - 其他文档（如对话整理、人员A/C 解析）可保留历史与细节，但应在文首或关键处引用上述两份清单，并避免把已实现项继续写在「待办」里。
- **测试文档**：明确「主清单」与「引用关系」，减少重复维护；优先更新与当前环境一致的内容（如账号密码、在库/组长等）。
- **过时表述**：按《对话整理与待办方案》已列出的 D1、D2、D3 等执行，删除或改写易误导的差异描述，并同步批量导入指南等。

### 3.2 建议的文档结构（在现有五类目录基础上微调）

保持现有 `需求与设计 / 开发与使用 / 测试 / 迁移与部署 / 方案与报告` 五类不变，做如下增强：

- **方案与报告**  
  - **新增或明确**：  
    - **《已完成事项清单》**（建议新建，或合并进《文档修订意见》附录）：仅列已实现并可在当前代码中验证的事项，并注明对应文档/模块（如 T1/T2/T3/T4、任务12/13、实物名称映射、状态「在库」、组长过滤等）。  
    - **《当前待办事项清单》**（建议新建，或与《对话整理与待办方案》第四部分拆分）：仅列**尚未实现或尚未闭环**的事项（如 D1/D2/D3/D4 等文档类待办，以及若仍有代码类待办则单独列出）。
  - 《对话整理与待办方案》可保留为「历史对话结论 + 执行方案」，但其中 T1–T4、任务12/13 等已实现项应改为「已完成」，并引用《已完成事项清单》；待办部分只保留真正未做事项，并引用《当前待办事项清单》。  
  - 《人员A工作完成情况与人员C工作解析》建议在篇首增加「与当前代码状态对照」说明，并删除或改写「按大类/按实物名称」差异段落（D1）。
- **测试**  
  - **主清单**：建议以《核心功能测试优先清单》为**投产前优先执行的主清单**（其已定义顺序与核心用例），并在 `docs/README.md` 和《功能测试文档》开头明确写清：「执行时以《核心功能测试优先清单》+《测试文档260304》对应章节为主清单，测试用例第一/二部分为详细步骤参考。」  
  - **其余测试文档**：功能测试文档、测试用例第一/二部分可保留，但与大段重复的段落改为「见核心功能测试优先清单 / 测试文档260304 用例 ID xxx」等引用，减少多处同步。  
  - **环境与账号**：在《核心功能测试优先清单》《测试文档260304》《功能测试文档》中统一默认管理员密码为当前 `init_db.py` 实际值（如 `1234567`），或明确说明「以 init_db 输出为准」。
- **需求与设计**  
  - 《资产导入字段扩展方案》《删除与导入逻辑优化方案》保持为方案主文档；实施已完成，可在文末或「实施记录」中注明「已按本方案在 xx 分支实施」，并与《已完成事项清单》对应。  
  - 《批量导入指南》与导入列名、必填/可选列、示例表头与《资产导入字段扩展方案》同步（D2），避免两处不一致。

## 四、建议执行顺序

1. **先做文档结构与清单**
  - 新增《已完成事项清单》与《当前待办事项清单》（可先放在《文档修订意见》附录或单独文件）。  
  - 在《对话整理与待办方案》《人员A工作完成情况与人员C工作解析》中引用这两份清单，并把已实现项从「待办」移入「已完成」。
2. **再做内容修订**
  - D1：人员A解析中差异表述删除/改写。  
  - D3：测试主清单说明写入核心功能测试优先清单或联动方案。  
  - 测试文档中管理员密码/环境说明统一。
3. **最后做同步与可选**
  - D2：批量导入指南与资产导入字段扩展方案同步。  
  - D4（可选）：数据模型与外键说明文档。
