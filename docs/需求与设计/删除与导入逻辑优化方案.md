# 删除与导入逻辑优化方案

本文档仅给出方案与建议，不直接改动代码。实施时再按方案在代码中落地。

---

## 一、要解决的问题

1. **删除逻辑**：避免因外键依赖复杂而导致「想删的数据删不掉」；统一策略后，删除操作可预期、不报错。
2. **导入与逻辑删除的配合**：资产逻辑删除后再次用同一份数据（如同一资产编号）导入时，希望**不发生冲突**，或**直接通过改动逻辑删除标识实现恢复并更新**，而不是报错或产生重复数据。

---

## 二、删除逻辑优化方案

### 2.1 原则

- **核心业务实体尽量采用逻辑删除**，不物理删行，从源头避免外键「被引用行不存在」的问题。
- **谁引用谁，谁负责「可见性」**：被引用方做逻辑删除后，查询方通过「只查未删除」过滤即可，无需级联物理删除。
- **物理删除仅用于「无被引用」或「子表/临时数据」**；若必须物理删「被引用」的主表，则需在应用层先处理关联（置空、转移或禁止删除）。

### 2.2 分实体建议

| 实体 | 现状 | 建议 | 说明 |
|------|------|------|------|
| **Asset（资产）** | 已逻辑删除 | 保持 | 继续用 `deleted_at` / `deleted_by_id`，查询统一加 `deleted_at.is_(None)`。 |
| **SafetyCheckType** | 已逻辑删除（is_active） | 保持 | 继续用「停用」不删行。 |
| **SafetyCheckTask** | 已逻辑删除（status=cancelled） | 保持 | 取消即改状态，不删行。 |
| **User（用户）** | 物理删除 | **改为逻辑删除** | 增加 `deleted_at`（及可选 `deleted_by_id`），删除时只置这两项；列表/登录等查询加「未删除」条件。这样不会再有「删用户时被 assets / transfer_requests 等外键挡住」的问题。 |
| **TransferRequest / AssetEditRequest** | 物理删除 | 可保持 | 二者为「申请单」，无其它表的外键指向它们，物理删即可。若希望可审计，可改为逻辑删除（如加 `cancelled_at`）。 |
| **SafetyCheckAssetTypeMapping** | 物理删除 | 可保持 | 配置表，无子表引用。 |
| **PendingReallocation** | 物理删除 | 可保持 | 流程用完即删，符合业务。 |

### 2.3 用户逻辑删除时的外键处理

- **不删行、只打标**：用户「删除」后，`users` 表该行仍在，所有指向 `users.id` 的外键仍然有效，**不会触发外键约束错误**。
- **业务含义**：  
  - 若希望「已删除用户」不再出现在下拉、分配、登录等，在所有「查用户」的接口里加条件（如 `User.deleted_at.is_(None)`）即可。  
  - 历史数据（如某资产的 `user_id` 仍指向已删除用户）可保留；展示时按需显示「已删除用户」或占位文案。
- **可选**：若希望资产列表里「使用人」不显示已删除用户，可在展示层将「已删除用户」映射为「未知/已离职」等，而不必把 `assets.user_id` 置空，避免大面积更新和唯一性约束问题。

### 2.4 不推荐的做法

- **不推荐**：为「能删掉用户」而在数据库层对大量外键加 `ON DELETE CASCADE` 或 `ON DELETE SET NULL`。会导致误删或数据成片置空，难以控制和审计。
- **推荐**：用逻辑删除让「行一直在」，外键关系保持简单、可预测。

## 三、导入与逻辑删除的配合（再次导入不冲突）

### 3.1 现状简要

- 当前导入：若「资产编号」在库里**已存在且未删除**，则静默跳过该行（不报错、不覆盖）。
- 若「资产编号」已存在且**已逻辑删除**，当前逻辑会走「新建」分支，因唯一约束 `asset_number` 会报错，造成「再次导入该数据时发生冲突」。

### 3.2 目标行为

- **同一资产编号再次导入时**：  
  - 若库中**无**该编号 → 正常新增。  
  - 若库中**有**该编号且**未删除** → 保持现有「跳过」或改为「按策略选择：跳过 / 覆盖」。  
  - 若库中**有**该编号且**已逻辑删除** → **不报错、不冲突**：直接**恢复该条并用 Excel 更新**（即把逻辑删除标识改掉，并用本行 Excel 数据更新该记录）。

### 3.3 推荐实现思路（导入流程中的分支）

在导入循环中，对每一行的「资产编号」做如下分支（不写具体代码，只描述逻辑）：

1. **按资产编号查库**  
   - 先查「未删除」：`asset_number = 当前行编号 AND deleted_at IS NULL`。  
   - 再查「含已删除」：`asset_number = 当前行编号`（不限制 deleted_at），用于判断是否曾存在。

2. **若存在且未删除**  
   - 保持现状：静默跳过（或按产品需求改为「用本行 Excel 覆盖该资产」）。

3. **若存在且已删除**（即该编号在库里有一条，但 `deleted_at` 非空）  
   - **不再走新增**，避免触发唯一约束。  
   - **直接复用该行**：  
     - 将 `deleted_at` 置为 `NULL`，`deleted_by_id` 置为 `NULL`（即恢复逻辑删除标识）；  
     - 用当前 Excel 行数据更新该资产其余字段（所属大类、实物名称、规格型号、状态、存放信息、使用人等，与当前「新建时写入」的字段一致）；  
     - 若导入时有「使用人」且需要联动下发安检任务，可在此分支同样调用一次联动任务创建逻辑。  
   - 这样：**同一数据再次导入 = 恢复 + 更新**，不会冲突，也不会多出一条重复资产。

4. **若不存在**  
   - 按现有逻辑新增一条资产。

### 3.4 小结（再次导入不冲突）

- **冲突来源**：同一资产编号在「已逻辑删除」时仍占一行，再导入会尝试插入，触发唯一约束。  
- **解决方式**：导入时若发现该编号**已存在且已逻辑删除**，则**只改逻辑删除标识（恢复）并更新该行**，不插入新行。  
- 这样既满足「逻辑删除后再次导入不冲突」，又满足「直接通过改动逻辑删除标识完成恢复」的需求。

---

## 四、实施顺序建议

1. **用户逻辑删除**（可选但推荐）  
   - 在 `User` 表增加 `deleted_at`（及可选 `deleted_by_id`）。  
   - 删除用户接口改为只更新这两字段；所有「查用户列表 / 有效用户」的查询加 `deleted_at.is_(None)`。  
   - 这样删除逻辑不再受外键阻塞。

2. **资产导入与逻辑删除的配合**  
   - 在导入逻辑中按「3.3」增加分支：  
     - 先查该资产编号是否存在（含已删除）；  
     - 若存在且已删除 → 恢复（清空 `deleted_at`/`deleted_by_id`）并更新本行 Excel 数据；  
     - 若存在且未删除 → 跳过（或按需覆盖）；  
     - 若不存在 → 新增。  

按以上顺序做，即可在**不改动现有物理删除的级联关系**的前提下，保证「想删的能删掉（通过逻辑删除）」「再次导入不冲突且能通过改逻辑删除标识恢复」。
